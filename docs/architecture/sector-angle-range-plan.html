Persist Sector Angle Ranges Instead Of Deriving Them From Sector Number

Recommended plan for changing backend/src/lib/db/schema.ts so each sector stores its angular span directly, while preserving sector numbers as stable coordinate/order identifiers.

Decision Store sector geometry as the full scalar Range shape: numeric type, max-bound type, min angle, and max angle.
API shape Expose an angleRange DTO from the stored row values instead of hardcoding range semantics while reading.
Migration Add required columns directly. No backfill is needed because this project can tear down and recreate the early database.

Why This Shape

The current model stores sector_number only. That is enough for coordinates like 01:02, but it forces every renderer to infer equal-sized sectors by counting siblings in the same orbit. Persisting the angle range makes the backend the source of truth for render geometry and lets future generation create uneven sector sizes without a frontend contract change.

Keep sector_number. It is still useful for coordinates, deterministic ordering, and movement graph readability. The new columns describe geometry, not identity. The database should store the Range metadata too, so a repository read is a rehydration step, not a place that silently assumes float and exclusive.

Database Storage

Column Type Nullability Meaning
angle_numeric_type varchar(16) not null Stored Range.numericType. Initial generated sectors should use float.
angle_max_bound_type varchar(16) not null Stored Range.maxBoundType. Initial generated sectors should use exclusive.
start_angle_degrees double precision not null Stored Range.min: the inclusive lower bound of the sector angle, measured clockwise from 12 o'clock.
end_angle_degrees double precision not null Stored Range.max: the upper bound of the sector angle, measured clockwise from 12 o'clock.

Use doublePrecision from Drizzle for the bounds rather than integer, because unequal sectors may produce fractional angles. Store degrees instead of radians because the existing architecture doc and frontend SVG plan already describe sectors in degrees. Use scalar columns instead of JSON so generated migrations, row assertions, and DB constraints stay readable.

Do not store the whole Range object as JSON. Store every field as an explicit scalar column, then rehydrate the object in the repository read model.

Range Contract

Use the published @guillaume-docquier/tools-ts Range type at repository/controller boundaries, not the legacy backend/src/lib/Range.ts type. The repository read model should use the broad Range type because the DB row owns numericType and maxBoundType: 

type SectorAngleRange = Range

The initial generation code can still create ranges like this:

{
  numericType: "float",
  maxBoundType: "exclusive",
  min: 0,
  max: 90
}

Never create Range objects manually in backend code. Use Range.create when building trusted generated/test data or rehydrating DB rows protected by constraints. Use Range.safeCreate only for untrusted input, and handle both success and failure explicitly. The DTO should include the resulting object under angleRange. The frontend receives explicit semantics from the database-backed API value without importing runtime backend code.

Migration Plan

  1. Add required columns directly to sectors: angle_numeric_type, angle_max_bound_type, start_angle_degrees, and end_angle_degrees.
  2. Add single-row check constraints for angle_numeric_type in ('float', 'integer'), angle_max_bound_type in ('inclusive', 'exclusive'), start_angle_degrees >= 0, end_angle_degrees <= 360, and start_angle_degrees < end_angle_degrees.
  3. Tear down and recreate the local/dev database instead of backfilling existing sector rows. Seed or generated-game flows should create fresh sectors with the new required Range fields.

Rollback is still just dropping these columns while the database is disposable. Once real data matters, rollback loses persisted geometry information unless another artifact stores the sector angle ranges.

Implementation Order

  1. Update schema and generate the Drizzle migration.
  2. Review the generated migration for the four required columns and check constraints.
  3. Update repository write/read models and row mapping.
  4. Update controller DTOs and router tests so the API contract is explicit.
  5. Update repository tests so persisted rows prove the DB shape.
  6. Reset the local/dev database instead of backfilling it.
  7. Update the architecture doc and, when the actual renderer is built, consume angleRange on the frontend.

Recommended Test Paths

  • Repository create persists angle_numeric_type, angle_max_bound_type, start_angle_degrees, and end_angle_degrees.
  • Repository read model returns angleRange using the row values for numericType, maxBoundType, min, and max.
  • Router response includes angleRange for every sector.
  • Migration has no backfill path and requires fresh sector inserts to provide all Range columns.
  • Later renderer test/manual check confirms frontend uses persisted angles, not sector count arithmetic.

Open Decision

There is no longer a backfill decision. I recommend adding DB check constraints for single-row invariants in the first migration, but not trying to enforce no overlap or full 360-degree coverage in SQL. Cross-row geometry invariants belong in the generation/controller flow where all sectors for an orbit are available at once.

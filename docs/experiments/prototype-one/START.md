# Heirs of Sol Prototype 1 launch prompt

Orchestrate the implementation of Heirs of Sol Prototype 1 in the existing `codex/prototype-one-experiment` worktree and draft PR. You own the requirements, decisions, and acceptance of all 28 increments. Delegate all implementation, diff review, and hands-on verification. Keep your own review at the level of the rules, acceptance criteria, and subagent conclusions. Keep diffs, test output, mutation reports, screenshots, and browser traces in the agents' work contexts. Ask for a focused follow-up whenever a report leaves a criterion unanswered.

Read [the epic](issues/00-prototype-one-epic-and-match-rules.md), the [ordered checklist](PROGRESS.md), and all linked local descriptions first. The copies define the scope. Use them offline. Never access or change GitHub issues, their comments, relationships, labels, or project items, directly or through tools, workflows, or delegated agents. Keep ticket numbers, live issue links, and issue-linking keywords out of branch names, commits, PR text, and comments. Keep the single PR in draft and leave the merge decision to the human.

The run is unattended. Direct every subagent to bring questions, conflicting requirements, and technical blockers to you. Decide product behavior, tuning, and technical trade-offs using the epic, the local acceptance criteria, accepted decisions, and the running system. Record each ruling and its reason in [RUN-LOG.md](RUN-LOG.md) as soon as you make it, then tell the affected agents. Never pause to ask the human. Follow repository and scoped instructions. If a durable change needs human approval, keep the accepted decision in force, choose a compatible approach for the experiment, and record the proposal for review after the run.

Keep a short note in [PROGRESS.md](PROGRESS.md) identifying the active increment, who owns outstanding work, and the next action. After context compaction or a restart, read that note, the linked increment, and its relevant run-log entries. Check the status of outstanding assignments before dispatching more work.

## Player interface

The increment descriptions specify gameplay and provide no mockups or wireframes. Give UI workers the player’s task and the information they need to complete it. Favor simple layouts, familiar controls, and the game’s existing terminology. Label buttons with the action they perform and dropdown options with names players can distinguish. Use visual cues where they clarify game state. Skip decorative animation and parallax.

For each player-facing increment, give the verification agent a player task to perform in the running UI. Ask whether the player can find the relevant information, operate the controls, and tell what happened. For example, after submitting a move, the player should be able to tell where the ship is now and where it will go when the turn resolves.

## For each increment

1. **Define the behavior before dispatch.** Read the local increment, its dependencies, and the existing behavioral requirements at the affected entry points. Identify the rules that already apply. Write the exact wording of each new or revised requirement in the assignment, including its preconditions and observable outcome. Have the worker apply those requirements beside the entry point using the repository workflow. If implementation reveals a missing rule, decide its wording and send it back to the worker.
2. **Dispatch an implementer and an independent reviewer together.** Give both the local increment, requirements, acceptance criteria, relevant decisions, and scope of ownership. Choose each agent's model and reasoning effort for its task. Include the GitHub ticket restriction in every assignment. While the implementer works, the reviewer can identify risks and edge cases from the requirements.
3. **Give the reviewer ownership of the diff.** The reviewer inspects the implementation and tests and sends actionable findings directly to the implementer. The implementer makes corrections and asks for another review. Repeat until the reviewer clears the final changes. Have the reviewer check behavioral test names against stable requirement IDs, fast-check properties against the relevant invariants, and replay information for failures. For changes to galaxy creation or turn resolution, have the implementation team run the applicable mutation suite, address observable gaps, and record the disposition of surviving and uncovered mutants.
4. **Dispatch an independent verification agent for each increment.** Specify the acceptance criteria, the scenarios that exercise them, and the expected observable outcomes. Have the verifier use the appropriate entry point, including persistence checks, checks from different players' views, and the UI walkthrough where applicable. The verifier sends failures and reproduction steps to the implementer, then repeats the affected checks after corrections. Product questions come to you for a ruling.
5. **Accept the increment from concise reports.** The reviewer reports the reviewed commit and any open findings. The verifier reports the verified commit, a result for each acceptance criterion, and any gaps. Compare those summaries with your requirements. If a check is missing or a later fix affects a result, send it back to the responsible agent. Have agents put detailed findings and evidence in the run log or link them there.
6. **Preserve the implementation history.** Require at least one distinct implementation commit for this increment on the experiment branch before marking it complete. Use the increment prefix and a readable description in the commit subject, for example `03a: open planets in a full planet view`. Split an increment into more commits when it helps review. Keep each implementation commit specific to one increment and preserve it in the draft PR history. Record its commit hash or hashes and verification summary in [PROGRESS.md](PROGRESS.md) when you check off the increment.

Maintain [RUN-LOG.md](RUN-LOG.md) throughout the run. Record every ambiguity, decision, finding, and problem with the affected increment, evidence, chosen action, reason, and observed result. Include failed approaches and limitations of the stack or workflows. After each accepted increment, dispatch the next one. When a dependency is blocked, delegate independent work and return to the blocker. Continue through failed tests, review findings, and recoverable tooling failures.

Dispatch verification agents to exercise the integrated solo supply chain, multiplayer handoffs and scoring, and both match endings. Use their summaries to direct any repairs and repeat checks. Push the accepted branch to the existing draft PR. Finish the log with outstanding limitations and the decisions most worth human review.

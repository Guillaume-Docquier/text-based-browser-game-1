## Correctness and architecture conclusions

The shared evaluator is the actual decision path at frontend selection, authoritative API submission, and locked resolution. Renamed target/input tags are resolved by mappings and effect discriminants. Standard content stays backend-owned; shared Test content is independently defined. Costs, speed, range, replacement, commitments, and partial candidate feedback come from parsed Ruleset data. Stationary Assault uses the same positive stationary-presence predicate as combat; transit origins do not become defenders.

The factory captures a concrete bounded Assault definition and stable definition ordinal into a new journey, omitting the future Assault from the current effect pool. Arrival processing preserves captured movement before clearing/removing the incoming row, retains each order's initiating tick/journey/submission independently of the actual merged survivor, and updates prior intents through merge rebindings. Ordinary arrivals add strength without gaining an Assault. Multiple owners sharing a pooled Action ID and multiple friendly orders sharing a survivor retain separate outcomes. Completion/destruction removes the journey-based occupancy without a new lock table or history mechanism.

All departures and arrivals precede Build and Combat. Build execution and effect construction are canonical; combat uses one global canonical tick queue with persisted descending Fisher–Yates ties, no singleton draw, and no removal or reshuffle of dead queued candidates. The single simultaneous exchange uses every stationary enemy, preserves ownership, and uses exact bigint products/quotients/remainders with stable Fleet-ID remainder ties. Supported strengths are branded safe integers; unsafe loaded values and relevant aggregate overflow fail before costs/RNG. Removed source, merged child, and combat-dead IDs reach the existing worker delete/upsert seam.

The existing turn-row `FOR NO KEY UPDATE` transaction still encloses authoritative decision reads, replacement/cancellation and write. No API dependency was introduced into the worker and no app runtime import was introduced into shared code. Expected data/gameplay failures return typed Results at changed core seams. Movement JSON is stored in the existing column; no empty migration was added for the new JSON shape.

The concrete intent/rebinding/queue seams are justified by the actual supported arrival composition. I found no harmful duplicated gameplay rule, speculative workflow framework, or missing generalization that would materially simplify multiple live mechanics. Minor similar sorting/rebinding fragments do not justify an unrelated abstraction. Existing Systems and glossary accurately describe implemented normal Assault while preserving planned combat/planet scope.

## Queue ownership check

I traced the current manual-deadline fixture through the real queue predicates. `games.repository.ts` initializes `turnsProcessing.scheduledFor` from `gameTurn.endsAt`. The corrected fixtures use `ControlledClock({ startDate: new Date() })` and a one-hour turn interval. `markDueTurnsAwaitingProcessing` changes only `turns.status` and `closedAt`; it does not alter the queue row's `scheduledFor`. `getNextTurnForProcessing` selects only queue rows with `scheduledFor <= since` and null `processingStartedAt`.

The explicit test processor advances its private controlled clock by two hours before marking due and claiming the turn. The forked API worker instead runs `entry.turn-processing.ts` with production `Clock`, polling every second. It therefore sees the unchanged one-hour real deadline still in the future during the normal sub-hour test execution and cannot claim those manually due rows. This is distinct from the former Ready path, which sets queue `scheduledFor` to real `closedAt`; the two actual real-clock Ready/deadline races remain in C and passed. This source-backed trace closes the current fixture-race concern without disabling the background worker or changing production code. If a future fixture could run for an hour of wall time, its real worker could become eligible; a future test-support adjustment should widen/assert the deadline margin or explicitly coordinate worker timing while retaining the separate real-clock race coverage.

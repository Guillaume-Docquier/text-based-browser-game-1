## Correctness and architecture assessment

Colonize is a supported effect plus validated unclaimed-planet constraint. Both independent Standard and Test content compose the same mechanics with their own content values. The shared evaluator reserves selected strength once for Move+Colonize and reserves configured consumption for stationary Colonize; budgets exclude the edited instance and include the full retained submission set. API authorization and locked validation use the same evaluator. No action-name, ID or tier branch implements gameplay.

Arrival bindings retain actual effect type, original definition ordinal, mappings, configured requirement, action identity and departure provenance. Movement advances genuine journeys once, settles/merges before later phases, and rebinds pending intents to the surviving fleet without borrowing its minimum arrival tick. Combat remains explicit; ordinary Move and enemy presence do not imply Assault. Colonization runs after combat/current reinforcement, filters invalid contenders before tied shuffle, uses canonical ordinal provenance and persisted tools-ts descending Fisher-Yates RNG, and checks current ownership/current strength again on application. Failure-to-claim is Prevented, without another payment, return or consumption. Exactly zero strength removes the actual survivor and records its deletion.

Owner changes are projected only for changed planets. Worker load, resolved projection and repository save preserve game identity; the owner update predicate contains gameId, planetId and prior null owner, with the game's player FK. Resources, fleets/deletions, completed/processing timestamps, ownership, next turn/actions/schedule and RNG save in the same transaction. The invalid-owner test alters the production save model through an explicit subclass seam and calls the real repository transaction; it does not fake persistence. Its publicly reached setup and comprehensive before/after row snapshots test atomic rollback.

UI text/controls consume configured definitions and mapped tags. Galaxy selection stores IDs and re-reads the selected system/planet from the latest PlayerView, which prevents stale owner objects in the open system/details pane. Planets/map/details retain exact owner alias assertions. Existing planet attributes/maxPopulation displays remain; there is no Population/Colony production, development bonus, outcome-history store, new System/GDDR, environment edit or empty migration.
